# Система планирования обслуживания бытовой техники

Приложение для планирования и контроля обслуживания бытовой техники с консольным и шаблонным веб-интерфейсом Django.

## Назначение

Проект предназначен для хранения и обработки информации о планируемом обслуживании бытовых устройств. Программа позволяет загружать задачи из JSON-файла, проверять сроки обслуживания и находить просроченные задачи.

## Целевая аудитория

Основными пользователями являются владельцы бытовой техники, а также специалисты и небольшие сервисные организации, занимающиеся ее обслуживанием.

## Предметная область

Бытовая техника требует регулярного технического обслуживания. Для устройств необходимо хранить информацию о планируемых работах и сроках их выполнения.

Основными сущностями проекта являются устройство, обслуживание, задача и дата.

## Возможности

* загрузка задач из JSON-файла;
* сохранение задач в JSON-файл;
* определение статуса обслуживания;
* расчет даты следующего обслуживания;
* поиск просроченных задач;
* сортировка задач по дате;
* обработка ошибок при работе с данными;
* автоматизированное тестирование функций;
* просмотр устройств и задач на страницах Django;
* карточки объектов и пользовательская страница ошибки 404;
* Django-шаблоны с наследованием, включаемыми компонентами и контекстом;
* собственные CSS, JavaScript и изображение через Django static files.
* SQLite-база с SQL-схемой, импортом JSON и запросами для веб-страниц;
* поиск задач до выбранной даты и страница статистики по устройствам и статусам.

## Веб-интерфейс

Страницы получают данные через Django ORM (`maintenance_web/queries.py`). Модели `homepage.User`, `devices.Device` и `maintenance_tasks.Task` связаны внешними ключами с `PROTECT`: нельзя удалить владельца или устройство, пока на них ссылаются записи. `User` предметной области не заменяет встроенного пользователя Django для входа в admin.

Список `/tasks/` поддерживает параметры `q` (название задачи или устройства), `until` (дата включительно), `device` и `owner` (ID), `status` и `sort` (`date`, `-date`, `priority`, `device`). Условия объединяются, затем применяется стабильная сортировка с дополнительным `pk` и пагинация по 5 записей. Переходы сохраняют GET-параметры. Некорректные фильтры выводят сообщение и пустую выборку; неизвестная сортировка также отмечается ошибкой. Некорректный номер страницы обрабатывает `Paginator.get_page()`.

## База данных и переход ПР9

Рабочая база веб-приложения: `db.sqlite3`, структура управляется миграциями. База ПР7 `data/maintenance.sqlite` сохранена как источник переноса. SQL-файлы и `db/` остаются материалами ПР7; веб-представления их не вызывают. Консольный интерфейс сохраняет отдельные JSON-репозитории и не синхронизируется с ORM автоматически.

```bash
poetry run python manage.py migrate
poetry run python manage.py import_pr7
poetry run python manage.py check
poetry run python manage.py showmigrations
poetry run python manage.py runserver
```

Если базы ПР7 ещё нет, сначала выполните `poetry run python -m db.import_json`. Произвольный источник: `manage.py import_pr7 --source path/to/maintenance.sqlite`. Импорт читает источник без права записи, сохраняет ID, проверяет поля и связи, выполняется одной транзакцией. Целевые предметные таблицы должны быть пустыми; повторный запуск завершается понятной ошибкой без изменения данных. Перед переносом существующей рабочей базы сохраните её резервную копию.

Миграции: `homepage/0001_initial`, `devices/0001_initial`, `maintenance_tasks/0001_initial`. Проверка отсутствия неоформленных изменений: `manage.py makemigrations --check --dry-run`. Пример SQL миграции: `manage.py sqlmigrate maintenance_tasks 0001`.

CRUD доступен через ORM в shell и настроенные модели Django admin. Новые формы изменения данных в публичном интерфейсе в эту работу не входят.

```python
from homepage.models import User
from devices.models import Device
from maintenance_tasks.models import Task
user = User.objects.create(name="Тест", email="test@example.com")
device = Device.objects.create(owner=user, name="Чайник", category="Кухня")
device.name = "Новый чайник"
device.full_clean()
device.save()
Device.objects.get(pk=device.pk)
device.delete()
user.delete()
```

`full_clean()` проверяет владельца задачи, диапазон приоритета и значения полей. `save()` автоматически его не вызывает. Ограничения допустимых статусов, ролей, интервала и приоритета дополнительно созданы в БД. Для загрузки связанных объектов используется `select_related`, для статистики `Count`, `values` и `annotate`; устройства без задач сохраняются в статистике с нулём.

## Объектная модель

* `User` хранит имя, email и роль пользователя.
* `Device` хранит владельца, категорию, бренд, модель, дату последнего обслуживания и интервал. Метод `mark_serviced()` обновляет обслуживание, свойство `next_service_date` рассчитывает следующий срок.
* `Task` хранит задачу для устройства, дату, приоритет и статус. Методы `start()`, `complete()` и `cancel()` защищают переходы состояния.
* `DeviceService` и `TaskService` содержат бизнес-сценарии и проверяют принадлежность данных пользователю.
* `UserRepository`, `DeviceRepository` и `TaskRepository` предоставляют операции `find_by_id`, `find_by_owner`, `create`, `update`, `delete`.

## ПР10 Административная панель и ORM

Админка находится по адресу `/admin/`. Для входа используется встроенный пользователь Django с `is_staff` и разрешениями, а не модель `homepage.User` предметной области. Чтобы создать свою учётную запись, выполните:

```bash
poetry run python manage.py createsuperuser
```

Русские названия приложений, моделей и полей оформлены в AppConfig, Meta и verbose_name. Для устройств настроены поиск, фильтры категории и бренда, сортировка, редактирование интервала прямо в списке и вычисляемая дата следующего обслуживания. Для пользователей доступны поиск по имени и email и фильтр роли. Списки админки содержат по 20 записей.

У задач доступны поиск по названию, устройству и владельцу, фильтры статуса, приоритета и даты, календарная иерархия и автодополнение связей. Связанные задачи показаны в карточках устройств и владельцев как inline только для чтения со ссылкой на редактирование задачи. Это позволяет менять задачу через полноценную форму с проверкой совпадения владельцев. Массовые действия доступны только с правом change_task: отмена меняет только planned/in_progress, возврат в план только cancelled; completed не затрагивается.

`TaskQuerySet` предоставляет цепочки `active()`, `cancelled()`, `completed()`, `for_date()`, `with_related()` и `for_list()`. Активными считаются planned и in_progress; менеджер по умолчанию не скрывает другие состояния. Список задач получает словари через `annotate(F(...)).values(...)`, карточка использует объекты с `select_related`. Статистика дополнена общими и условными подсчётами `aggregate(Count(..., filter=Q(...)))`.

На `/devices/?available_on=2026-11-05` можно найти устройства без незавершённых задач на выбранную дату. Подзапрос `active().for_date().values_list()` исключает занятые устройства. Отменённые и завершённые задачи устройство не исключают. Это критерий наличия задач обслуживания, а не технической исправности устройства.

У устройств появился уникальный ASCII slug и `get_absolute_url()`. Существующие записи получили адреса `device-<id>` миграцией данных, новые получают `device-<uuid>`. Адрес сохраняется при переименовании устройства. Новые ссылки открывают `/devices/<slug>/`, прежние адреса `/devices/<id>/` продолжают работать. Добавление slug выполнено поэтапно: nullable поле, заполнение существующих строк, обязательное поле с генератором значения. TextChoices статусов уже присутствовал в ПР9, поэтому повторное преобразование статусов не требуется. GeneratedField не добавлялся: дата следующего обслуживания рассчитывается существующим свойством; изменение модели демонстрируется на slug и локализации.

Контекстный процессор `homepage.context_processors.site_context` передаёт название сайта и количество устройств в общий шаблон. Он выполняет один дополнительный COUNT на HTML-страницу.

### Анализ SQL

Django Debug Toolbar добавлен в dev-зависимости. При `DEBUG=True` он подключается для localhost (`127.0.0.1`, `::1`); при запуске pytest и manage.py test отключён. В production с DEBUG=False приложение, middleware и маршруты панели не подключаются. Настройка следует [документации Django Debug Toolbar](https://django-debug-toolbar.readthedocs.io/en/stable/installation.html).

Запустите `poetry run python manage.py runserver`, откройте список задач, карточку и статистику. Во вкладке SQL найдите JOIN, COUNT и выборку текущей страницы. Проверка реальных локальных HTML-запросов с включённой панелью дала: список задач 5 SQL-запросов, карточка 2, статистика 4. Список выполняет COUNT пагинатора, выборку словарей текущей страницы, загрузку вариантов устройств и владельцев и COUNT контекстного процессора. Карточка загружает задачу и её связи одним JOIN плюс общий COUNT. Авторизация и админка могут добавлять запросы сессии и разрешений.

Проверки ПР10: права просмотра и изменения в admin, поиск и inline, массовые действия, валидация владельца, методы QuerySet, условная статистика, устройства без активных задач, slug, вычисляемая дата и постоянное число SQL-запросов списка.
